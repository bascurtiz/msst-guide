# Training Audio Source Separation Models — guide site

A static website version of *“Training vocal removers locally and on the cloud”*
(original PDF by **Meskvlla33**), rewritten with a consistent chapter structure,
a dark UI-themed design system, a troubleshooting index and reference appendices.

No dependencies and no framework — plain HTML, one stylesheet and one small
script. The five pages are rendered from templates by a dependency-free Node
script: `src/pages/*.html` holds the markup and `content/pages/*.json` holds the
text, and `node tools/build.mjs` writes the pages. That split is what lets the
guide's original author edit the words in a browser (`/admin/`) without ever
touching markup — see **Editing** below.

## Structure

```
index.html        GENERATED — Home: overview, quick start, chapter map, local vs cloud
data.html         GENERATED — 02–04: requirements, dataset, validation set
setup.html        GENERATED — 05–07: repository, commands & arguments, YAML
training.html     GENERATED — 08–12: from scratch, focus shifting, fullness, local, cloud
reference.html    GENERATED — 13 + A–D: troubleshooting index, glossary, metrics
src/pages/*.html      Templates: the shell, diagrams, code samples, tables, calculator.
                      Prose positions are marked with `<!--c:key:mode-->` slots.
content/pages/*.json  The prose itself, as markdown, one file per page.
admin/index.html      The content editor (Sveltia CMS, loaded from a CDN)
admin/config.yml      Which content files it edits
admin/SETUP.md        How to set up the editor's GitHub login, and how to deploy
assets/css/site.css   Design system: dark + light palettes (sampled from the MVSEP UI)
assets/js/site.js     Reading progress, TOC scroll-spy, copy buttons, drawer, search
assets/js/search-index.js  GENERATED search index
assets/uploads/       Images the editor inserts
assets/fonts/         Self-hosted Montserrat (variable woff2, latin + latin-ext)
assets/img/*.png      Figures extracted from the original PDF
assets/img/favicon.*  Site icon: the header waveform mark
assets/img/og-image.png · twitter-card.png  Social preview cards
robots.txt · sitemap.xml   Generated by tools/seo.py
_headers              Cloudflare Pages response headers: noindex for the editor, font caching
dist/ · training-guide.zip  GENERATED by tools/package-site.mjs — the deployable subset
```

Every page shares the same shell: sticky header with section navigation, a
two-column body (article + on-page contents), and a previous/next pager. Each
chapter follows the same shape — overview, steps, caveats, errors.

Every page is committed already rendered, so the root *is* the site and a host
needs no build command and no output directory — `python -m http.server` in the
root serves exactly what a reader gets.

Upload hosts are the exception, because they publish everything they are handed
and the root also holds `src/`, `content/`, `tools/` (with 1.5 MB of source fonts)
and this README. For those, `node tools/package-site.mjs` stages the site-only
subset into `dist/` and zips it as `training-guide.zip`: five pages, `assets/`,
`admin/`, `robots.txt`, `sitemap.xml`, `_headers` — and nothing else. It doubles
as a check, resolving every local `href`, `src` and `url()` against the staged
tree and refusing to emit a bundle that would 404.

## Run it locally

```bash
node tools/build.mjs
python -m http.server 8123
# then open http://127.0.0.1:8123/
```

Opening `index.html` directly from disk also works — including search, which
reads a bundled index rather than fetching pages.

## Tools

The build is one dependency-free Node script, because that is what a build
container is guaranteed to have. The Python helpers are stdlib-only (except
Pillow for the icon/card renderers) and write into the project.

```bash
node tools/build.mjs             # render the pages, rebuild the search index, re-stamp assets
node tools/build.mjs --check     # report whether the committed pages are current (exit 1 if not)
node tools/package-site.mjs      # render, stage dist/, zip the upload bundle (also: --no-build, --no-zip, --out)
node tools/extract-content.mjs   # one-time: split hand-written pages into templates + content
node tools/lib/md.test.mjs       # unit tests for the renderer: node --test tools/lib/md.test.mjs

python tools/seo.py              # regenerate sitemap.xml + robots.txt
python tools/make-og-image.py    # re-render the social cards (needs Pillow)
python tools/make-favicon.py     # re-render the PNG icon fallbacks
python tools/fetch-fonts.py      # re-download Montserrat (only if refreshing it)
python tools/add-heading-ids.py  # give a hand-added heading an anchor id (templates)
```

`tools/build-search-index.py` and `tools/stamp-assets.py` are superseded — the
build does both, so the ordering rule they needed (rebuild the index, *then*
stamp) no longer exists. They are kept only for reference.

If the build reports a problem, it exits non-zero and names the file: a slot in a
template with no text behind it, or text with no slot to go in. Both mean the
template and the content file have drifted apart, and both are worth stopping
for — a warning here is a paragraph that would otherwise silently disappear from
the site.

## Asset caching

`site.css`, `site.js` and `search-index.js` are referenced as
`assets/css/site.css?v=eb270005` and friends. The stamp is the first eight hex
digits of the file's MD5, and the build writes the current value into every page
table it renders — so the stamps are never stale and there is no counter to bump
by hand. (That used to be a manual step, and getting the order wrong once
shipped a cached search index: it is now structural.)

## Search

`assets/js/search-index.js` holds one entry per paragraph, list item, table cell,
code block and heading (`[page, section, anchor, sub-heading, kind, text]`).
`assets/js/site.js` injects the search panel, groups matches by section, ranks
them (title and sub-heading matches score highest, command lines are demoted as
excerpts unless you searched for a `--flag`) and shows the count as
*“N hits in M sections”*. Open it with the header button, `/`, or `Ctrl`/`Cmd`+`K`;
`↑`/`↓` move between results, `Esc` closes.

## Share links

Every `h2`/`h3` on a page — the home page included — carries a share button,
revealed on hover or keyboard focus next to a faint pencil-grey icon. It copies
`origin + pathname + #id` — deliberately *without* the query string, and using the
heading's permanent `id` rather than a generated one, so the link keeps working
after a rebuild. On touch devices (where `(hover: none)` matches and a hidden
control would be unreachable) it stays faintly visible and opens the system share
sheet instead of copying, if the browser has `navigator.share`.

The selector is `main h2, main h3` rather than `article …`: the home page has no
`article` element, and nothing else inside `main` (the on-page contents, the
pager) contains an `h2`/`h3`, so no navigation chrome picks up a button.

The ids themselves live in the HTML, put there by `tools/add-heading-ids.py` — they
have to, or a shared link would not scroll on first load, before `site.js` runs.
The script leaves existing ids alone and is safe to re-run; `site.js` falls back to
slugging the heading text only for a heading added without running it. The result
is announced through a visually hidden `role="status"` line (*“Link copied: …”*),
and the button is hidden in print along with the rest of the chrome.

## Search engine metadata

The canonical, Open Graph and Twitter tags assume the site is served from
**`https://msst-guide.pages.dev`**. If you host it elsewhere, change that domain
in the five `<head>` blocks (a find-and-replace of the domain is enough) and in
`tools/seo.py`, then rerun `python tools/seo.py`.

Each page carries a unique title and description, `og:*` / `twitter:*` tags with
a 1200×630 card (`og-image.png`) and a 1200×600 one for X (`twitter-card.png`),
plus JSON-LD: a `Book` with its chapters on the home page, and a `TechArticle`,
`WebPage` and `BreadcrumbList` per section. `robots.txt` allows everything and
points at `sitemap.xml`.

## Typography

Montserrat (SIL OFL 1.1) is self-hosted from `assets/fonts/`, variable weight
400–800, split into latin and latin-ext subsets so readers who never type a
Latin-extended character never download that file. Each page preloads the latin
subset in its `<head>`; the preload link is redundant if your host already pushes
friendly caching, but it removes the font from the critical path.

Sizes are tuned for the wider face: body 15.5 px, a 68-character measure on
paragraphs, and slightly tighter tracking on headings. Monospace labels, code and
metrics keep their own stack. To swap the typeface, replace the four `@font-face`
blocks and the `--sans` token.

## Interactive parts

The chunk size & VRAM calculator (`#calc` in `setup.html`) is plain DOM code in
`assets/js/site.js`: inputs update on `input`/`change`, the results block is
`aria-live`, and the target preset buttons set the sample rate.

**The window is `chunk_size`, in samples — the one key every architecture reads.**
`dim_t` is the same value in frames (`floor(chunk_size ÷ hop_length) + 1`, because
every STFT in this ecosystem pads with `center=True`), so the `dim_t` dropdown of
the four documented frame counts *writes* `chunk_size`, and its **user-defined**
checkbox frees the number for anything else — the same pattern as the sample rate.
Editing `chunk_size` writes the frame count back into that control, so the two can
never disagree, and a window that is not a whole number of hops raises a note
saying so (MSST tolerates it — its own SCNet config is 485 100 ÷ 1 024 = 473.7).

**An `architecture` select decides which block owns the STFT** — `ARCHS` in the
script. A Roformer reads `model.stft_n_fft` / `model.stft_hop_length` and ignores
the `audio` copies next to them (viperx's shipped config annotates them
`# don't work (use in model)`); mdx23c and DTTNet are handed the whole `audio`
block; SCNet uses `model.nfft` / `model.hop_size`. Picking a family sets that
family's real defaults, the key hints under `n_fft` and `hop_length`, and the note
under the grid saying where the settings live.

**Memory follows the frame count, which is why the hop moves it.** At a fixed
window, half the hop is twice the frames, so the estimate scales with
`batch_size × dim_t` while the window stays put. The sample rate reaches the
estimate only through `rate ÷ hop_length`: under `rate ÷ 100` (441 — every
published Roformer) that ratio is 100 frames per second at any full-band rate and
halving the rate changes nothing, while under a fixed hop it halves the frames.
*auto* derives the hop from a rule you choose — `rate ÷ 100`, `n_fft ÷ 4` (512, the
MSST templates and DTTNet) or `n_fft ÷ 8` (mdx23c) — and unticking it lets you type
one by hand. `n_fft` is an input for that reason; the `hop_length and n_fft` section
in `setup.html` carries the table of which block owns what, with the real configs
behind each rule.

The **target presets** explain what band each stem needs, and all five keep the full
band by default: nothing in this ecosystem is published below 44.1 kHz and a
Roformer's mel filterbank is built from `model.sample_rate`, so a halved run is
training from scratch. Bass and Guitar DI are the two targets where halving has a
real argument, and their notes say so — plus how to test it (the `user-defined`
checkbox under sample rate, then a 44.1 kHz baseline to compare against).

Both dropdowns have a *user-defined* escape hatch where *auto* would be: ticking it
below **sample rate** swaps the list for a free field (1 000–192 000 Hz, snapped
into range on blur). A rate outside the four documented ones raises a `Custom rate`
note. Below **hop_length** it is the reverse — *auto* is on by default, and unticking it
hides the rule and lets you type a hop by hand.

Conversions are exact (`chunk_size = (dim_t − 1) × hop_length`, window = `chunk_size ÷
sample rate`). The memory figure is an estimate scaled from the one documented data
point — a **stereo** Roformer (`num_channels: 2`, `stereo: true`, like every
checkpoint in the ecosystem) at `batch_size: 4` and `dim_t: 1333` (13.32 s at
`hop_length: 441`) filling a 140 GB H200 — anchored on **frames and batch size, not
samples**. The other two families' defaults are that figure *extrapolated*, and the
readout label says so: there is no mdx23c, DTTNet or SCNet measurement to check it
against. Selecting *Mono (1 ch)* halves it, because the band-split front end folds
the two channels into one sequence (`MONO_FACTOR` in the script). If you change the
anchor, update the calculator's method note and the JS comment so the two stay
honest together.

## Graphics

Diagrams are hand-authored HTML/CSS plus inline SVG — no image files, no chart
library, and every colour comes from a token so they work in both themes:

| Component | Used for |
|---|---|
| `.flow` | Numbered pipeline cards (home workflow, cloud walkthrough) |
| `.meters` | Comparing finite resources (VRAM tiers) |
| `.layers` | Frozen vs. trained stages of a fine-tuned model |
| `.panel-grid` | Side-by-side file types (config vs. checkpoint) |
| `.fig-shot` + `.pin` / `.pin-list` | Numbered annotations over a screenshot |
| `.balance` | Two-way trade-offs (fullness vs. bleedless) |
| `.schematic` | Inline SVG figures: waveforms, chunk windows, convergence curves |

Schematic SVGs use a `0 0 620 *` viewBox with these classes: `grid`, `axis`,
`track`, `band`, `band-b`, `win`, `line-a` (cyan), `line-b` (amber), `lbl`, `hd`.
Wrap one in `<div class="fig-scroll">` so narrow screens pan it instead of
shrinking the labels to nothing. Add `figcaption` text that says what to look at,
and label illustrative drawings as schematics rather than measured data.

Figures that sit inside a `.fig` should be wrapped in `.fig-scroll`; the sheet
gives them a 560 px minimum so the 11 px SVG labels stay legible on phones.

## Dark / light theme

The switch in the header is a segmented sun/moon control. The choice is stored in
`localStorage` under `msst-theme` and applied by a tiny inline script before the
stylesheet loads, so there is no flash of the wrong theme. With no stored choice
the site follows the operating system's `prefers-color-scheme`.

Both palettes live in `assets/css/site.css`: the dark tokens in `:root`, the light
overrides in `[data-theme="light"]`. Add a colour to both blocks rather than to a
component rule, and the whole site follows. `<meta name="theme-color">` is updated
by `assets/js/site.js` so mobile browser chrome matches.

Scrollbars follow the theme too: `color-scheme` is set per theme (which also
themes form controls and the native bars), and `scrollbar-color` plus
`::-webkit-scrollbar` rules give the bar the site's line colour.

### Phones

Verified down to 360×780 (Galaxy S23 class): no horizontal overflow on any page,
header controls grow to ~40 px touch targets, tables scroll inside their own
container, the on-page contents turns into a chip list, and `viewport-fit=cover`
plus `env(safe-area-inset-*)` padding keeps fixed elements out of rounded corners
and the gesture bar. Wide figures and schematic SVGs pan inside `.fig-scroll`
rather than shrinking their labels.

## Print / PDF

Every page has a **Save as PDF** button in the header, and a dedicated print
stylesheet: navigation is hidden, colours invert to a light theme for paper, and
sections avoid page breaks inside tables, code blocks and figures.

## Favicon

`assets/img/favicon.svg` is the icon itself — the same waveform mark used in the
header, on a dark rounded tile so it reads in both light and dark browser chrome.
Browsers that do not use SVG icons fall back to `favicon-32.png`; iOS/iPadOS uses
`apple-touch-icon.png` and Android `favicon-192.png`. Regenerate the PNGs after

```bash

```

## The repository

The site lives at **<https://github.com/bascurtiz/msst-guide>** (public, default
branch `main`), and that is what `admin/config.yml` points the editor at.

What is committed is the source *and* the output: the five rendered pages, plus
`src/`, `content/`, `tools/`, `assets/` and `admin/`. `dist/` and
`training-guide.zip` are the only things ignored, because `tools/package-site.mjs`
rebuilds them. Committing the rendered pages is what keeps the root servable by
anything, with no build step and no output directory to configure.

`.github/workflows/build.yml` runs on a push that touches `content/`, `src/`,
`tools/`, `assets/css/` or `assets/js/site.js` — that is, on an editor's save. It
tests the renderer, re-renders the pages and commits them if they changed, so
the repository is always current even for someone browsing it. A save that
changes nothing produces no commit: a re-render of the committed pages is
byte-identical, on Linux as well as Windows.

Publishing is the one thing left to configure, and it depends on how the Pages
project was made. **`admin/SETUP.md` §4** covers both routes: connect the project
to this repository and it publishes on every push, or keep uploading by hand and
add two repository secrets so the workflow publishes for you. The live site is
currently behind the repository — its `robots.txt` has no `Disallow: /admin/`,
so it was deployed before the editor existed.

## Editing

### The text — by the guide's author, in a browser

`/admin/` is a content editor. Sign in with GitHub, pick a chapter, edit the
paragraphs, save: the CMS commits `content/pages/<page>.json`, the build renders
the pages, and the site is live about a minute later. `admin/SETUP.md` has the
one-time login setup (a personal access token, or a "sign in with GitHub" button
via a small Cloudflare Worker) and the deploy notes — including the one thing
that decides whether saving publishes at all: on a Git-connected Pages project
the host renders and republishes itself, while a project filled by direct upload
needs the repository's workflow to do it.

What the editor can reach: every paragraph, list item, sub-heading, card title,
label and figure caption, on all five pages. What it deliberately cannot: the SVG
diagrams, code samples, tables, the chunk-size calculator, the sidebar, the table
of contents, the pager and the footer — those carry layout and data a rich-text
editor cannot represent safely, so they stay in the templates and change in code.

Two rules the build enforces rather than trusts: a block's **key** ties the text
to its slot in the template (rename it and the build stops), and a block's
**styling comes from the slot** (an intro line stays an intro line).

### The layout — in the templates

Prose lives behind a marker comment:

```html
<!--c:index.head.p.03:prose:p| class="sub"-->
<h1><!--c:index.head.h1.02:inline--></h1>
```

- `prose` markers stand alone and replace one or more `<p>` (or `<blockquote>`,
  `<figcaption>`) elements. The author can add and remove paragraphs there, and
  the marker carries the element's own attributes so styling survives.
- `inline` markers sit *inside* an element that owns its look — a heading, list
  item, card title, `<b>`, `<span>` — and receive inline text only.

To add a prose block, put a marker in the template **and** add the matching
`{ key, label, md }` to that section's `blocks` in `content/pages/<page>.json`.
Key format is `<page>.<section>.<tag>.<nn>`, and any unique, stable key works.
Do one without the other and the build tells you which one is missing.

`tools/extract-content.mjs` created this split from the pre-migration pages and
can redo it (`--force --from <dir>`), but that re-derives every slot and key — it
is a migration tool, not an editing one, and it will discard authored text.

### The design

- Colours and typography live in the `:root` custom properties at the top of
  `assets/css/site.css`. Change them there and every page follows.
- To add a chapter: copy a section from a template, keep the `<h2 id="…">`
  anchor, and add a matching entry to that page's `<aside class="toc">`.
- Update the section nav and footer link lists on all five pages when adding a
  new page — those are template markup on each page, not generated.
